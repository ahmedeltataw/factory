## Scope

In M6, the Supervisor **reads** GitHub issue events for allow-listed repositories, turns the allowed ones into pending intake records, and a person approves each one with a CLI command; approval creates a normal task. Everything GitHub sends is untrusted data.

Out of M6: any GitHub write (comments, labels, PR, push, merge: they need Contents/Pull requests RW and come with M9/M10), the Lead Brain `admit` call (M8; M6 admission is deterministic rules plus a person), webhooks (manual 07 §8: no public endpoint), PR and review events, maintenance mode, quotas and per-actor budgets (M7; residual risk, Muse #22-m6: a compromised allow-listed account can fill `maxPendingPerRepo` pending rows per repo with tasks that wait for approval; nothing runs without a person's approve), `executors/background.ts`, secret storage in Windows Credential Manager (M6 reads the token from the environment; Credential Manager is a later card), a real-GitHub CI test (CI uses a fake HTTP server; the owner may run one real smoke at close).

The M6 token needs **Metadata R and Issues R only**, repository-scoped, expiry ≤ 30 days (manual 09 §4). Manual 09 §4 says one repository per token: the policy may list several repos, so the owner keeps the token's repository set equal to the policy's `repos` set exactly (a token that covers a repo the policy omits is harmless; a policy repo the token does not cover gives `404`, a non-retryable error shown in status). The owner writes `<state-dir>/github-policy.json` outside the Supervisor; the Supervisor only reads it and never writes it (Muse #22-m5).

## Frozen interfaces

### Layout

`supervisor/src/sources/github/`: `event.ts` (normalize, sanitize), `gate.ts` (policy and gate), `ports.ts` (the `GitHubPort` type), `fake.ts` (in-memory fake port), `ingest.ts` (dedupe and storage), `client.ts` (real HTTP port). `event.ts`, `gate.ts`, `ports.ts` are pure: no I/O, no imports outside `sources/github/` and `core/`. Only `client.ts` touches the network and the token.

### Port (read-only)

`GitHubPort.poll(input: { repo: string; etag: string | null }): Promise<PollResult>`, where `PollResult` is `{ kind: 'not-modified'; etag: string; pollAfterMs: number }` or `{ kind: 'events'; etag: string; pollAfterMs: number; events: unknown[] }` or `{ kind: 'rate-limited'; retryAfterMs: number }` (always ≥ 60 000: a missing, unparseable or past reset header gives 60 000; Muse #21-2) or `{ kind: 'error'; retryable: boolean; message: string }`. `events` are raw JSON values, validated by `normalizeEvent`, never trusted. The port has no write method and never returns the token. Both the real client and the fake implement it.

### Normalized event (`event.ts`)

- `normalizeEvent(raw: unknown): { ok: true; event: GhEvent } | { ok: false; reason: string }`. Handles two GitHub Events API types: `IssuesEvent` (`action` `opened`) and `IssueCommentEvent` (`action` `created`); every other type or action → `{ ok: false, reason: 'unsupported-event' }`. An event whose embedded `issue` has a `pull_request` key (GitHub sends PR comments as `IssueCommentEvent`) is also `unsupported-event` (Muse #21-1: PR events are out of M6). Malformed shape → `{ ok: false, reason: 'malformed' }` (zod, strict on the fields it reads, tolerant of extra fields).
- `GhEvent`: `{ eventId: string (GitHub event id, decimal string), repo: string ('owner/name', lower-cased), kind: 'issue.opened' | 'issue.comment', actor: { id: number, login: string, bot: boolean }, issue: number, labels: string[] (sorted, from the issue), createdAtMs: number, issueTitle: string, text: string, textTrust: 'untrusted' }`. `bot` is true when the actor `type` is `Bot` or the login ends with `[bot]`. `text` is the comment body (`issue.comment`) or the issue body (`issue.opened`); a `null` or missing body becomes `""` and is valid (Muse #21-4: an empty labelled issue from an allow-listed actor is admitted by its title); cut at 8 000 UTF-16 units on a code-point boundary, well-formed Unicode.
- `sanitizeLine(input: string): string`: removes C0/C1 control characters, bidi override and isolate characters (U+202A-202E, U+2066-2069), zero-width characters (U+200B-200D, U+FEFF), collapses whitespace runs to one space, trims, cuts at 200 code points. Used for every text that becomes a task title or a status line.

### Policy and gate (`gate.ts`)

- Policy file `<state-dir>/github-policy.json` (JSON, validated with zod; a missing file at start means GitHub intake is off). The Supervisor re-reads it before every poll round (Muse #21-8): a removal from `actors`, `repos` or `labels` applies from the next round, and a file that becomes missing or invalid pauses all polling with the error shown in status (fail closed; stored events are unaffected). Shape: `{ "version": 1, "repos": [{ "name": "owner/name" (lower-case; Muse #21-3), "labels": string[], "scope": string[] }], "actors": [{ "id": number, "login": string }], "command": "/factory task", "maxPendingPerRepo": number (1..100) }`. Policy `hash` = sha256 of the normalized JSON; stored with every admission.
- Exports (Lead amendment 2026-11-12: the names were not pinned, found while briefing the M6-01 protected tests). `event.ts`: `normalizeEvent`, `sanitizeLine`, type `GhEvent`. `gate.ts`: `parsePolicy(input: unknown): { ok: true; policy: Policy; hash: string } | { ok: false; reason: string }` (`input` is the already-parsed JSON value; `reason` names the first failing path, as path components such as `repos`, `0`, `name`, in any separator style; the keys are checked in the order `version`, `repos`, `actors`, `command`, `maxPendingPerRepo`, and an unknown key is reported after those, so the first failure is deterministic), `gate`, types `Policy` (the parsed shape below, same keys) and `GateResult`. `Policy` is deep-frozen by `parsePolicy`; `hash` is the lower-case sha256 hex of `JSON.stringify` of the policy with the keys of every object sorted recursively (compact, no whitespace; arrays keep their order), and `gate` takes a `Policy` from `parsePolicy` only.
- `gate(policy, event): GateResult`, deterministic, checks in this order; first failure wins and gives the reason code:
  1. `repo-not-allowed`: repo not in `repos`.
  2. `bot-actor`: `actor.bot` (manual 10 §5: ignore bot-authored events).
  3. `actor-not-allowed`: actor id not in `actors` (id must match; a login match with another id is rejected, so a renamed or recycled login gets no rights).
  4. `label-not-allowed`: the issue carries none of the repo's `labels`.
  5. For `issue.comment`: the first non-blank line of `text`, trimmed, must be the command (`/factory task`) alone, or the command followed by one or more spaces/tabs and an argument (the rest of the trimmed line); anything else, such as `/factory tasks`, is `no-command`. A command with only whitespace after it has no argument and takes the issue-title form (Muse #21-9). For `issue.opened`: no command is needed (the allow-listed actor opening a labelled issue is the instruction).
  - Result: `{ admit: false, reason }` or `{ admit: true, title, scope, basis }`. `title` = `sanitizeLine(argument)` for a command with an argument, else `sanitizeLine('#<issue> ' + issueTitle)`; empty after sanitizing → `empty-title`. **`scope` comes only from the policy repo entry (path prefixes inside the task worktree, validated at policy load with `parseScope` from `core/scope.ts`, the same validator as `task create --scope`; `.` means everything; Muse #21-6); text never supplies scope, phase, dependencies or a command id.** `basis` = `{ policyVersion, policyHash, actorId, repo, issue, eventId, kind }`.
- A GitHub comment edit is never an instruction: only `created` is accepted, and a stored event is never re-read from GitHub.

### Schema v8 (migration 8, one transactional step: `BEGIN IMMEDIATE`, each statement a separate `db.exec`, future versions refused unmodified, as M3-M5)

- `CREATE TABLE github_events (event_id TEXT NOT NULL, project_id TEXT NOT NULL REFERENCES projects(id), repo TEXT NOT NULL, kind TEXT NOT NULL CHECK (kind IN ('issue.opened','issue.comment')), actor_id INTEGER NOT NULL, actor_login TEXT NOT NULL, issue INTEGER NOT NULL, status TEXT NOT NULL CHECK (status IN ('ignored','pending','approved','rejected')), reason TEXT, title TEXT, scope_json TEXT, basis_json TEXT, text TEXT NOT NULL, text_trust TEXT NOT NULL CHECK (text_trust = 'untrusted'), text_sha256 TEXT NOT NULL, event_at TEXT NOT NULL, received_at TEXT NOT NULL, decided_at TEXT, decided_by_command TEXT REFERENCES commands(id), task_id TEXT REFERENCES tasks(id), PRIMARY KEY (project_id, event_id))`. `ignored` rows have `reason` and no `title`/`scope_json`; `pending` rows have both and `basis_json`.
- `CREATE TABLE github_cursor (project_id TEXT NOT NULL REFERENCES projects(id), repo TEXT NOT NULL, etag TEXT, next_poll_ms INTEGER NOT NULL, error TEXT, updated_at TEXT NOT NULL, PRIMARY KEY (project_id, repo))`.
- Triggers: `github_events_no_delete` (BEFORE DELETE aborts); `github_events_immutable` (BEFORE UPDATE aborts unless `OLD.status = 'pending'` and `NEW.status IN ('approved','rejected')` and every column except `status`, `reason`, `decided_at`, `decided_by_command`, `task_id` is unchanged, and `approved` has a `task_id`); a CHECK-by-trigger that a `pending` insert has a non-empty `title` and `scope_json`.
- Existing data: no data step. A v7 database gets two empty tables; no existing row changes. `status` of a v7-shaped project is unchanged except `schemaVersion` and the new fields (M6-07).

### Ingest (`ingest.ts`, called by the Supervisor inside `fencedWrite`)

- `ingestPoll(db, projectId, policy, repo, result, nowMs)`:
  - `events`: events are processed oldest first (GitHub returns newest first; sort by `eventId` compared as `BigInt`, never as `Number`; Muse #21-5). **Dedupe by `(project_id, event_id)`: an event already stored is skipped, whatever its first outcome.** Each new event is normalized then gated: a failure of `normalizeEvent` for an `unsupported-event` is not stored (it would fill the table with noise); a `malformed` event is stored `ignored` only if it has a readable event id; a gated-out event is stored `ignored` with the reason; an admitted event is stored `pending`, except that if the repo already has `maxPendingPerRepo` pending rows it is stored `ignored` with reason `pending-limit`. The cursor `etag` and `next_poll_ms` (`nowMs + pollAfterMs`, never less than 60 000) are stored in the same transaction.
  - `not-modified`: only the cursor moves. `rate-limited`: `next_poll_ms = nowMs + retryAfterMs` (honours the reset), nothing else. `error` with `retryable`: `next_poll_ms = nowMs + backoff` (60 s, doubling per consecutive error up to 15 min, kept in memory; a restart resets it). A non-retryable error stops polling that repo until the next Supervisor start (the stop lives in memory only, so a restart resumes polling) and its sanitized message is written to `github_cursor.error` in the same transaction; a later successful poll clears it. A retryable error also writes `error` and clears on success.
  - Never writes a `commands` row and never creates a task: only a person's approve does.
- Requests: one conditional (`If-None-Match`) request per repo per poll for page 1; the client follows `Link: rel="next"` for at most 2 more pages (300 events, all the Events API keeps), only to the same origin, and returns the pages concatenated with the ETag of page 1. Events beyond that window are not retrievable; this loss window is accepted (Muse #21-10), and M6 has no gap detection. A `304` costs no rate limit.

### Commands and CLI (exit codes 0/1/2 and Arabic messages as M3-M5)

- `factory github approve --state-dir <d> --event <eventId> [--command-id <uuid>]` → command kind `github.approve`, payload `{ "eventId": string }`. `factory github reject ... --event <eventId> [--reason <text>]` → `github.reject`, payload `{ "eventId", "reason": string | null }`. `--event` must be 1..20 digits (invalid → exit 2, no row). Same command id with the same payload → `duplicate`; other payload → exit 1.
- Apply `github.approve`: the event must exist in this project and be `pending`, otherwise `rejected` (`unknown event`, `event is not pending`). Then, in one transaction: a task is created from the event's `title` and `scope_json` through the same apply path as `task.create` (open phase, no dependencies; `created_by_command` = the approve command, and the task id = the approve command id, as `task.create` does), the event becomes `approved` with `task_id`, `decided_at`, `decided_by_command`. Traceability from the task to GitHub is the event row (`github_events.task_id` = the task id, with `repo`, `issue`, `event_id`); the task and the approve command payload carry no `source` field (Lead amendment 2026-11-13, found briefing the M6-04 protected tests: schema v8 has no task payload column and the approve payload is frozen as `{ eventId }`). A project with no phase rows is phase-less (M5 amendment) and applies as in M4. If the task apply path rejects (for example the stored scope no longer validates), the approve command is `rejected` with that reason, nothing is written, and the event stays `pending` (Muse #21-6).
- Apply `github.reject`: the event must be `pending` → `rejected` with the reason sanitized (`sanitizeLine`); otherwise `rejected`.
- A second approve of the same event under a new command id → `rejected` (`event is not pending`): at most one task per GitHub event.
- Task creation from GitHub is **always approval-required in M6**; there is no auto-admit switch.

### Supervisor loop

- When a policy exists, each tick, after reconcile and command drain and before dispatch, the Supervisor polls every repo whose `next_poll_ms <= now` (one repo at a time, awaited, with a 20 s timeout; a timeout is a retryable error) and calls `ingestPoll`. Dispatch, scheduling and recovery are unchanged. With no policy file, the loop is the M5 loop (no cursor reads, no port).
- The port is injected: tests pass `fake.ts`; production builds the real client from `client.ts` only when a policy exists **and** the token env var is set; a policy without a token → startup refuses with an Arabic message naming the variable (not its value).
- A `pending` event keeps the Supervisor busy? No: pending events wait for a person and never keep `--exit-when-idle` alive. A poll that is due keeps it busy until done: `runTick` returns `idle: false` while any repo poll is due (CHK-M6-05-d).

### Token isolation (`client.ts` and executors)

- The token is read once from `FACTORY_GITHUB_TOKEN` by the Supervisor process only, and held in a closure in `client.ts`. It is never written to SQLite, files, `commands`, evidence, status, logs, error messages or events. Errors from the client are rebuilt from status code and a fixed message; any string that contains the token is redacted to `[redacted]` before it leaves `client.ts`.
- Workers: `spawnWorker` in `supervisor/src/app/process-tree.ts` (the only place a worker process is spawned) removes `FACTORY_GITHUB_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN` and `GITHUB_PAT` from the child environment (also for grandchildren, they inherit).
- The real client sends `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, a fixed `User-Agent`, `If-None-Match` when it has an ETag, and only `GET /repos/{owner}/{name}/events?per_page=100` plus the same-origin `next` links of that response (at most 2). The base URL is configurable by env `FACTORY_GITHUB_API_URL` (default `https://api.github.com`) for the fake server; any other host is refused unless it is `127.0.0.1`/`localhost`.
- Rate limit: `x-ratelimit-remaining` = 0 → `rate-limited` with `retryAfterMs` from `x-ratelimit-reset` (or `retry-after`), never below 60 000, and 60 000 when the header is missing, unparseable or already past; 403/429 with those headers likewise; `x-poll-interval` → `pollAfterMs` (at least 60 s).

### Status additions (`--json`; the Arabic view shows the same facts)

- Top level adds `github: null | { repos: [{ name, lastPollAt, nextPollAt, etag: boolean, error: string | null }], events: { ignored, pending, approved, rejected }, pending: [{ eventId, repo, issue, actor, title, scope, receivedAt }] }` (`null` when no policy; `pending` newest 20, oldest first). Titles and logins shown come from stored sanitized values; `text` is never in status.
- `schemaVersion` becomes 8. The new field is always present.
