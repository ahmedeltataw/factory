## Frozen interfaces

### Phases

- Phase names and order are fixed: `intake` (1), `development` (2), `qa` (3), `devops` (4), `handover` (5).
- Phase status: `locked`, `open`, `done`. Each project has exactly one row per phase. At most one phase is `open`. Phases open in order; a `done` phase never reopens.
- A new project (`factory init`) gets `intake` `open` and the other four `locked`, in the same transaction that creates the project.

### Schema v7 (migration 7, one transactional step, same rules as M3/M4: `BEGIN IMMEDIATE`, each statement a separate `db.exec`, future versions refused unmodified)

- `CREATE TABLE phases (project_id TEXT NOT NULL REFERENCES projects(id), name TEXT NOT NULL CHECK (name IN ('intake','development','qa','devops','handover')), ord INTEGER NOT NULL CHECK (ord BETWEEN 1 AND 5), status TEXT NOT NULL CHECK (status IN ('locked','open','done')), opened_at TEXT, closed_at TEXT, PRIMARY KEY (project_id, name), UNIQUE (project_id, ord), CHECK (ord = CASE name WHEN 'intake' THEN 1 WHEN 'development' THEN 2 WHEN 'qa' THEN 3 WHEN 'devops' THEN 4 WHEN 'handover' THEN 5 END))` (SQLite CHECK allows no subquery)
- `CREATE UNIQUE INDEX phases_one_open ON phases(project_id) WHERE status = 'open'`
- `CREATE TRIGGER phases_no_delete BEFORE DELETE ON phases BEGIN SELECT RAISE(ABORT, 'phases are permanent'); END`
- `ALTER TABLE tasks ADD COLUMN phase TEXT NOT NULL DEFAULT 'intake' CHECK (phase IN ('intake','development','qa','devops','handover'))`
- `CREATE TABLE task_deps (task_id TEXT NOT NULL REFERENCES tasks(id), depends_on TEXT NOT NULL REFERENCES tasks(id), PRIMARY KEY (task_id, depends_on), CHECK (task_id <> depends_on))`
- `CREATE TRIGGER task_deps_no_update BEFORE UPDATE ON task_deps BEGIN SELECT RAISE(ABORT, 'task_deps are immutable'); END` and the same `BEFORE DELETE` (`task_deps_no_delete`).
- Data step (same migration): for every existing project insert its five phases with `intake` `open` (`opened_at` = migration time) and the rest `locked`. Existing tasks get `phase` `intake` from the column default, so an upgraded M4 database keeps dispatching its tasks unchanged.

### Graph core (pure module `supervisor/src/core/graph.ts`, no I/O, no imports outside `core/`)

- `PHASES = ['intake','development','qa','devops','handover'] as const`; `type PhaseName`; `phaseOrd(name): 1..5`.
- `parseDeps(input: unknown): { ok: true; deps: string[] } | { ok: false; reason: string }`: an array of 0..32 strings, each 1..200 characters, well-formed Unicode, not blank after trim. Output deduplicated and sorted (code-unit order).
- `planDispatch(input: DispatchInput): DispatchPlan`, deterministic, used by the Supervisor loop and by status:
  - Input: `nowMs`; `phases: { name, status }[]`; `tasks: { id, status, phase, deps: string[], scope: string[], notBeforeMs }[]` in dispatch order (`created_at`, then `rowid`). Every dep id refers to a task in the list (the loader guarantees it).
  - Output: `{ schedule: string[], block: string[], wait: Wait[] }` (exactly these keys; Lead amendment 2026-11-11, the shape was not pinned, found reviewing the M5-04 protected tests). `schedule`: ready task ids to start now, in dispatch order. `block`: ready task ids that become `blocked`, in dispatch order. `wait`: one entry per ready task that is neither scheduled nor blocked, in dispatch order: `{ id, reason: 'phase-locked' | 'deps' | 'scope' | 'backoff', on: string[] }` (`on` = the unfinished dep ids for `deps`, the overlapping held task ids for `scope`, the phase name for `phase-locked`, `[]` for `backoff`).
  - Rules, in this order for each `ready` task:
    1. A task with a dep in status `dropped`, or a dep that is itself in `block` or already `blocked`, goes to `block` (transitively, in dispatch order; deps are always older, so one pass is enough).
    2. Phase not `open` → wait `phase-locked`. The task does not join `held`.
    3. A dep not `done` → wait `deps`. The task does not join `held`.
    4. Scope overlaps `held` (M4 rule, `scopesOverlap`) → wait `scope`, and it joins `held`.
    5. `notBeforeMs > nowMs` → wait `backoff`, and it joins `held`.
    6. Otherwise → `schedule`, and it joins `held`.
  - `held` starts as the scopes of all `progress` tasks (any phase). Rule 4–6 keep the M4 FIFO behaviour for runnable tasks; tasks held back by phase or deps never hold a scope, so a later-phase task can never block the open phase.

### Commands and CLI (exit codes 0/1/2 and Arabic messages as in M3/M4; first stdout line `created <id>` / `duplicate <id>` unchanged)

- `factory task create ... [--phase <name>] [--after <taskId>]...`. `--phase` is one of the five names (invalid → exit 2). `--after` is repeatable, validated with `parseDeps` (invalid → exit 2). Payload adds `"phase": string | null` (null when omitted) and `"deps": string[]` (normalized, `[]` when omitted). Duplicate detection compares the normalized payload. M4 payloads without these keys are applied with `phase` null and `deps` `[]`.
- Apply `task.create`: `phase` null → the project's `open` phase (if none is open, i.e. `handover` is done, → `rejected`). A named phase that is `done` → `rejected`. Each dep must be an existing task of the same project, not `dropped`, with `phaseOrd(dep.phase) <= phaseOrd(task.phase)`; otherwise → `rejected` with reason, and nothing is written. On success the task row and its `task_deps` rows are written in the same transaction. A task can only depend on tasks that already exist, so the graph stays acyclic by construction.
- `factory phase advance --state-dir <d> --phase <name> [--command-id <uuid>]` → command kind `phase.advance`, payload `{ "phase": string }`.
- Apply `phase.advance`: the named phase must be the `open` phase, and every task in that phase must be `done` or `dropped`. Then in one transaction: the phase → `done` (`closed_at`), the next phase (if any) → `open` (`opened_at`). Otherwise → `rejected` (`phase is not open` / `phase has unfinished tasks`). Advancing `handover` leaves no phase open.
- `task.kill` (M3) also accepts a `blocked` task (already allowed). `task.retry` (M4) is unchanged; a retried task's dependents that were `blocked` stay `blocked` (they are blocked only by a `dropped` dep, which is final).

### Supervisor loop

- Dispatch loads `ready` and `progress` tasks plus every task referenced as a dep, the deps and the phases, calls `planDispatch`, writes `blocked` for `block` ids, and calls `scheduleAttempt` for `schedule` ids, all inside the existing `fencedWrite`. Nothing else in the tick changes.
- Idle: a `ready` task whose phase is `locked`, or that waits on a dep that is `failed`, does not keep the Supervisor busy (`--exit-when-idle` exits). A `ready` task waiting for backoff, scope, or a dep that is `ready`/`progress` keeps it busy (M4 rule).
- After a restart, reconcile is unchanged (M3/M4): an interrupted task is re-scheduled at once; its phase is open because a phase cannot advance while it has unfinished tasks.

### Status additions (`--json`; Arabic view shows the same facts)

- Top level adds `phases: [{ name, ord, status, openedAt, closedAt, tasks: { ready, progress, blocked, failed, done, dropped } }]` in ord order (empty list before `init`).
- Each task adds `phase`, `dependsOn: string[]` (sorted), and `waiting: { reason, on } | null` (from `planDispatch`, for `ready` tasks only; `null` otherwise). M4 `blockedBy` keeps its M4 computation (the `progress` tasks whose scope overlaps this `ready` task) and values; it can differ from `waiting.on`, which also names held `ready` tasks.
- `schemaVersion` becomes 7. The new fields are always present (no shape detection from data).
