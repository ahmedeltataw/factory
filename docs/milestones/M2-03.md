# M2-03: Supervisor ownership lease

Status: local implementation card; storage and command work remain unaccepted pending review and CI. No GitHub upload or merge into `main` is authorized. This card does not implement the Supervisor loop or permit domain writes without later authorization and ownership checks.

## Storage and lock

Migration 4 creates one `supervisor_lease` row slot per project database with columns `id` (integer primary key constrained to 1), `owner_id` (nonempty text), `generation` (positive integer), `heartbeat_ms` (nonnegative integer), and `status` (`active` or `released`). Upgrade is transactional and preserves projects and commands. Update Lead-owned current-version tests from 3 to 4; historical evidence stays tied to its earlier SHA.

Use `fs-native-extensions` 1.5.3 `tryLock`/`unlock` on a dedicated `supervisor.lock` file inside the canonical state directory. Never delete or replace the lock file. The state directory is trusted local application state, not a client-controlled repository. Its `state.sqlite` must resolve to the same real path as the provided connection's main SQLite database; mismatch fails before acquiring ownership. Fail closed if the module, path, OS lock or SQLite operation fails. A live OS lock blocks another cooperative process even when its lease appears stale.

The resolved `state.sqlite` must reside as `state.sqlite` in the canonical state directory, rather than being a link to a database in another directory; otherwise separate directory locks could protect the same database. Reject databases with more than one filesystem hard link for the same reason. A canonical directory alias that resolves to the same directory is acceptable. Handle internals governing its file descriptor, clock, closure and loss state must not be caller-mutable at runtime. Invalid heartbeat/release arguments are rejected before changing or closing a still-valid handle, so callers can correct an input error.

## Interface

Export `acquireSupervisor(db, stateDir, options)` from `supervisor/src/app/supervisor-lease.ts`. `options` contains `nowMs` (nonnegative safe integer from the trusted local clock), `staleAfterMs` (positive safe integer), and optional `takeover` containing the exact observed `{ ownerId, generation, heartbeatMs }`. The caller supplies time from a trusted clock; these options must never be passed through untrusted commands. Each acquisition generates its own random UUID owner ID. Return a handle exposing immutable `ownerId`, `generation`, and methods `heartbeat(nowMs)` and `release(nowMs)`. Clock values must be nonnegative safe integers; a heartbeat before the last heartbeat is rejected. A closed or lost handle cannot heartbeat or release again.

After taking the OS lock, atomically create generation 1 if no lease exists, or increment the generation when the existing row is `released`. An `active` row always blocks a new acquisition, even if the OS lock is free, unless the heartbeat is at least `staleAfterMs` old and explicit takeover evidence matches its owner, generation and heartbeat exactly in the same transaction. Future heartbeats are never stale. Stale evidence, missing evidence or a still-fresh row fails without changing the row. All acquisition failures release the OS lock and close the lock handle while leaving the caller's database open.

Heartbeat updates only the active row matching this handle's owner and generation; no match is `LeaseLostError`, and the handle becomes unusable. Release updates only that same row to `released`, then releases the OS lock and closes its file handle. A failure while releasing must still close the lock handle and leave the lease in a recoverable state; never report successful release when the database update failed. An OS lock is not a guarantee against non-cooperating code or a substitute for authorization/fencing. Later cards must explicitly use the generation as a fence when applying state changes.

Heartbeat and release must not report success for updates inside a caller-owned SQLite transaction that may later roll back. If the connection is already in a transaction, heartbeat rejects without modifying the row or invalidating the held handle; release rejects without modifying the row and closes its OS lock as on other release failures. Neither operation may commit or roll back the caller's transaction. After rollback the persisted active row remains recoverable only under the explicit stale-evidence protocol.

If closing the OS lock descriptor fails, release must report an error even when the persisted row update succeeded. Always attempt descriptor closure even if explicit unlock fails, and never hide a descriptor-close failure behind a success return. A SQLite row marked `released` alone does not prove that the OS lock was relinquished.
