## Scope

In M7 the Supervisor limits how much work it starts: (1) a **parallel slot cap** per project, (2) a **quota ledger** per provider window with reserve before dispatch, settle after, release on failure, (3) **budget caps** at project, phase and task level with 70% / 90% / 100% thresholds, (4) **intake budgets** per actor per day (closes the M6 residual). All are visible in `status` and set by CLI commands.

Out of M7: real provider usage parsing (token events per CLI, M8+ adapters), provider-reported `QUOTA` classification and its manual-resume state (manual 11; M8+), model fallback and role allocation, a global quota manager shared across projects (Muse #28-6: until it lands, **never run two Supervisors against one provider account**, or split the account window by hand between their `quota set` values), cost in money, call-level caps (Muse #28-12: the unit is the attempt, so the task cap with `max_attempts` is the call level), Lead Brain calls, any GitHub write.

**Accepted deviations (Muse #28-5, -10, -11).** The 90% threshold is a status-only signal in M7: dispatch continues on the same model between 90% and 100% and nothing notifies the Designer (no notifier exists yet); the exposure is the last 10% of a cap. Quota waits keep the 1 s heartbeat tick (no sleep-until-timer; later). `nowMs` is wall-clock UTC ms (`Date.now()`); a forward clock jump shortens windows and a backward jump over-counts; accepted. Quota waits clear by themselves when the counted window slides (this is a counted ledger, not a provider-reported limit); budget stops need a person (`budget set` higher or `budget clear`).

**Unit.** One unit is one started attempt. Providers do not report usage yet, so every number is `source: counted`, never shown as remaining tokens.

## Frozen interfaces

### Schema v9 (`store.ts`)

- `project_limits(project_id PK → projects, max_parallel INTEGER NOT NULL CHECK (max_parallel >= 1), updated_at)`: no row = no cap.
- `quota_windows(project_id, provider TEXT, window_ms INTEGER CHECK (>= 1000), max_units INTEGER CHECK (>= 1), updated_at, PK(project_id, provider))`: no row = unlimited for that provider.
- `quota_reservations(id PK, project_id, attempt_id UNIQUE → attempts, provider, units INTEGER CHECK (= 1), state CHECK IN ('reserved','settled','released'), reserved_at_ms, closed_at_ms)`: state moves only reserved → settled | released; rows are never deleted.
- `budget_caps(project_id, level CHECK IN ('project','phase','task'), key TEXT, cap_units INTEGER CHECK (>= 1), updated_at, PK(project_id, level, key))`. `key` is `''` for `project`, the phase name for `phase`, the task id for `task` (Muse #28-13); status shows it as is.
- `tasks.provider TEXT NOT NULL DEFAULT 'default'` (added column; old rows get `default`; GitHub-approved tasks get `default`). Provider vocabulary (Muse #28-9): `^[a-z0-9][a-z0-9-]{0,31}$`; `task create --provider <p>` is valid only when `<p>` is `default` or has a `quota_windows` row in the project, else rejected `unknown-provider`; a provider whose window is later cleared keeps its tasks and becomes unlimited (accepted).
- Usage is always derived (count of `reserved` + `settled` reservations joined to tasks), never a stored counter.

### Slots and gates (`core/graph.ts`, pure)

`DispatchInput` gains optional `maxParallel: number | null` and `gates: Record<string, { reason: 'quota' | 'budget'; retryAtMs: number | null }>`. `WaitReason` gains `'slots' | 'quota' | 'budget'`, and `Wait` gains `retryAtMs?: number | null` (set for `quota`/`budget`; `gates` values become `{ reason: 'quota' | 'budget'; retryAtMs: number | null }`, Muse #28-22). In `planDispatch`, after the backoff check and before schedule: a task in `gates` waits with that reason (`on: []`), then if `running + scheduled >= maxParallel` it waits `slots` with `on` = the progress tasks. `running` = tasks in `progress`. Waiting for gates or slots does not join `held`. Absent `maxParallel` and `gates` give the M6 plan exactly.

### Ledger (`app/quota.ts`)

- `check(db, taskId, nowMs): { ok: true } | { ok: false; reason: 'quota' | 'budget'; retryAtMs: number | null }`: pure read. Counts the provider window (reservations with `reserved_at_ms > nowMs - window_ms` in state reserved or settled, plus one, ≤ `max_units`), then the caps in the order task, phase, project (usage = reserved + settled reservations joined to tasks, plus one, ≤ `cap_units`). `retryAtMs` = when the oldest counted reservation leaves the window (quota) or `null` (budget: a person must raise the cap). The loop uses `check` for `gates`; `reserve` calls the same function (Muse #28-7), so they cannot drift.
- `reserve(db, handle, taskId, attemptId, nowMs)`: runs `check`, on success inserts a `reserved` row carrying `attemptId` (the attempt row already exists in the same transaction, so the FK holds; Muse #28-1).
- `scheduleAttempt` (recovery.ts) returns `{ ok: true } | { ok: false; reason: 'quota' | 'budget' | 'max-attempts' }`. Order inside one transaction: task still `ready` and not in backoff → max-attempts check (a failed task has no reservation, Muse #28-20) → `check` → insert attempt → `reserve` with that id → task `progress` → outbox rows. A `check` failure creates **no** attempt and leaves the task `ready`. Both call sites (dispatch, `reconcileWorkers`) use it; in `reconcileWorkers` the old attempt is closed first, and a failed reserve leaves the task `ready` with no new attempt (Muse #28-2).
- `closeReservation(db, attemptId, nowMs)`: the one close function. If a `workers` row exists for the attempt (a worker was started: observable fact, Muse #28-3) the reservation becomes `settled`, otherwise `released` (no usage counted). Called by every code path that closes an attempt: `finishAttempt`, the worker-liveness timeout and lost branches, `reconcileWorkers` (all branches), the `attempt.kill` handler (killed after start → settled; killed while pending → released), `failExhaustedEffects`, and the `superseded` path of `attempt.start`. Closing is idempotent. Invariant (property test): no `reserved` row belongs to an attempt in a terminal status; `reconcileWorkers` also closes any such row it finds (belt and braces).
- Window boundary: a reservation made exactly `window_ms` ago no longer counts.
- Thresholds: `usagePct = floor(100 * used / cap)`; `warn` ≥ 70, `fallback-needed` ≥ 90, `stop` = `usagePct >= 100` (dispatch gate `budget`; Muse #28-16). A cap lowered below current usage stops dispatch, never kills running work.
- Budget API (`app/quota.ts`, added at M7-04 so that M7-07 status reuses it, Lead amendment 2026-11-15): `budgetState(used: number, cap: number): { pct: number; state: 'ok' | 'warn' | 'fallback-needed' | 'stop' }` is pure (`pct = floor(100 * used / cap)`, `cap >= 1`; `ok` < 70, `warn` 70..89, `fallback-needed` 90..99, `stop` >= 100). `budgetUsage(db, projectId): Array<{ level: 'project' | 'phase' | 'task'; key: string; cap: number; used: number; pct: number; state: ...same enum }>` reads `budget_caps` of the project ordered project, phase, task then by key; `used` = reserved + settled reservations joined to tasks of that scope (project: every task of the project; phase: tasks whose phase = key; task: that task id), no "plus one". `check` stops when `used + 1 > cap` for the first cap in the order task, phase, project.

### Loop wiring (`supervisor-loop.ts`)

In `dispatch-tasks`, `dispatchInput` adds `maxParallel` and the `gates` map (`check` for each ready task). `scheduleAttempt` does the reserve (see Ledger). `runTick` idle rule: a `slots` wait, or a `quota` wait with a non-null `retryAtMs`, keeps the loop busy; a `budget` wait does not (a person must act). Project dispatch state for status: `paused-budget` when any ready task waits `budget`, else `waiting-quota` when any waits `quota`, else `open`; resume rule: `budget set` higher or `budget clear` applies on the next tick, quota resumes by itself when the window slides (Muse #28-4).

### Intake budget (`sources/github/gate.ts`, `ingest.ts`)

Policy gets optional `maxPerActorPerDay` (1..1000, absent = no limit; policy `version` stays 1; **the M6 flood residual is closed only when the owner sets it; recommended value 20**, Muse #28-21). `ingestPoll` evaluates the count **per event as it is processed** (Muse #28-19: not once per poll): rows with that `actor_id` and `status` in `approved`/`pending` whose `Date.parse(received_at)` is `> nowMs - 86400000`; at the limit the event is stored `rejected` with reason `actor-daily-limit` (never silently dropped).

### Commands (`commands.ts`, `apply-commands.ts`, `cli/main.ts`)

Append-only commands, applied by the Supervisor only: `limits set --max-parallel <n> | --clear-parallel`, `quota set --provider <p> --window-ms <n> --max-units <n> | quota clear --provider <p>`, `budget set --level project|phase|task [--key <k>] --cap <n> | budget clear ...`, and `task create --provider <p>` (new optional flag). Frozen rejection reasons (Muse #28-18): `invalid-number` (not an integer ≥ 1, or `window-ms` < 1000), `unknown-level`, `missing-key` (phase/task level without `--key`), `key-not-allowed` (project level with `--key`), `unknown-key` (no such phase or task), `unknown-provider` (see Schema). Arabic human text, English identifiers.

### Status additions

`status --json` gains `dispatch: 'open' | 'waiting-quota' | 'paused-budget'` (always present; `open` when nothing is gated), `limits: null | { maxParallel, running, waitingSlots }`, `quota: null | { windows: [{ provider, windowMs, maxUnits, used, resetsAt }` (`resetsAt` is `null` when `used` is 0, Muse #28-17, else the ISO UTC time the oldest counted reservation leaves the window)`] }`, `budget: null | { caps: [{ level, key, cap, used, pct, state: 'ok'|'warn'|'fallback-needed'|'stop', source: 'counted' }] }`. `limits`, `quota`, `budget` are `null` when their tables are empty (M6 status unchanged otherwise except `schemaVersion` 9 and the new `dispatch`, which every exact-shape protected test gains in M7-07). Waiting tasks show reason `slots`, `quota` or `budget`.
